# Security and IAM

## Customer account (runtime)

- **No public endpoint:** the ALB scheme is `internal` and tasks get no public IP. The ALB accepts 443 only from
  `AllowedIngressCidr` / `AllowedSourceSecurityGroupId`, and CloudFormation rules reject `0.0.0.0/0`. Tasks accept
  8080 only from the ALB security group. The API and agent listen on loopback only.
- **Authentication:** ALB `authenticate-cognito` on every path except `/healthz` (and `/api/selftest` when
  `EnableSmokeTestPath=true`, an installation-test switch that should stay false in production; it is rate-limited
  and makes one fixed-prompt model call). The user pool is admin-create-only, has a 14-character password policy and
  optional or required TOTP MFA, and uses `PreventUserExistenceErrors`. The app client secret is generated by Cognito
  and used only by the ALB; it is never in source, the template, outputs or images. `/api/logout` clears the ALB
  session cookies and ends the Cognito session.
- **Task role** (`TaskRole`): only `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`, on the selected
  foundation model or inference profile in this account and Region, plus foundation models reached *through that
  profile* (`bedrock:InferenceProfileArn` condition). All three containers share the task role (a single-task
  trade-off). Only the agent calls Bedrock.
- **Execution role:** the AWS managed ECS execution policy (image pull, logs), `GetSecretValue` on the one secret, and
  `kms:Decrypt` via Secrets Manager only.
- **Encryption:** one customer-managed KMS key (rotation on, retained) encrypts the log groups, the secret and the
  alarm topic.
- **Logging:** structured JSON to stdout, recording method, path, status, durations and sizes. Prompts, replies,
  tokens and headers are not logged (tested). Logs stay in the customer account, with retention set by
  `LogRetentionDays`.
- **Images:** digest-pinned, non-root, minimal bases pinned by digest, unit-tested in a build stage, and scanned (ECR)
  before release.
- **No vendor access:** no cross-account roles, agents or telemetry in customer accounts.

## Seller account (pipeline)

One CodeBuild role per stage:

| Role | Can | Cannot |
| --- | --- | --- |
| BuildAndTest | push to and read the staging ECR repos, read scan findings | Marketplace API, Marketplace ECR, SNS, AssumeRole |
| CleanAccountTest | `sts:AssumeRole` on **only** `TEST_DEPLOY_ROLE_ARN`; read/write `releases/*` in the artifact bucket; read previous templates | Marketplace, ECR push |
| PublishImages | pull staging, push to the configured Marketplace ECR repositories | Catalog API |
| MarketplaceSubmit | `StartChangeSet` and `DescribeEntity` on the product entity, `ListChangeSets`; put/get versioned templates | ECR push, SNS |
| MarketplaceWait | `DescribeChangeSet` | anything else |
| MarketplaceVerify | `DescribeEntity` on the product; read manual attestations | anything else |
| AnnounceRelease | `sns:Publish` on the release topic only; announcement markers | Marketplace, ECR |

`Resource: "*"` appears only where the API offers no resource scoping (`ecr:GetAuthorizationToken`,
`aws-marketplace:ListChangeSets`, `aws-marketplace:DescribeChangeSet`); a test enforces this. Configuration is
non-secret plaintext. No credentials are stored in the pipeline, images or artifacts, and stage artifacts redact any
token, secret or credential fields. The pipeline stack asserts the configured seller account and Region.

### Test account role

Create `TEST_DEPLOY_ROLE_ARN` in the dedicated test account:

- **Trust:** only the seller account's CleanAccountTest CodeBuild role (`aws:PrincipalArn` condition on that role ARN).
- **Permissions:** CloudFormation create, update, delete and describe on stacks named `mkt-ct-*`; the services those
  stacks create (ECS, ELBv2, EC2 security groups, ENIs, VPC endpoints and the fixture VPC, Cognito, KMS, Logs,
  CloudWatch, SNS, IAM roles with a permissions boundary, Lambda for the probe); `lambda:InvokeFunction` on the probe;
  `tag:GetResources`; `iam:PassRole` limited to roles created by those stacks. Scope with `aws:ResourceTag/marketplace:clean-account-run`
  where the service supports it. Do not grant AdministratorAccess.
- The harness deletes only stacks tagged with its own run ID, and only retained resources carrying that tag.
  Pre-existing resources in the test account are never touched.

## CI (GitHub Actions)

The workflow has `contents: read` permissions, runs on `pull_request` (never `pull_request_target`), uses no secrets,
and pins every third-party action to a commit SHA. Fork code never sees credentials because there are none.
